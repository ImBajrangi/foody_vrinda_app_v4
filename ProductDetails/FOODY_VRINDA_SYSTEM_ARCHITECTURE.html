Foody Vrinda: Enterprise Risk Mitigation Blueprint

Production-grade specifications covering Hash-Chained Append-Only Ledgers, Multi-Actor Cash Reconciliation, Tri-Tier Geofencing, Continuous ETA Recalculation, and Row-Level Security.

🛒
1. Customer Lifecycle, Tri-Tier Geofence & Privacy
Verified identity, non-nullable user_id, caller ID masking & 16 explicit states
  • Strict Pre-Authentication: All orders require verified session tokens (user_id NOT NULL). Eliminates ghost orders and anonymous checkout abuse.
  • Saved Address Portfolio: Customers manage multiple addresses (Home 🏠, Work 🏢, Ashram/Hostel 📍) with precise Landmark, Unit/Floor, and Delivery Instructions.
  • Tri-Tier Geofence Verification:
    • < 100m: Normal doorstep verification.
    • 100m – 250m: Proximity warning + customer doorstep confirmation prompt.
    • > 250m: Delivery lock. Requires controlled supervisor override logged with an audit event.
  • Caller ID Masking: Sarathi phone numbers are routed through proxy/in-app channels rather than exposing personal numbers.
NEW ➔ CONFIRMED ➔ COOKING ➔ READY_FOR_PICKUP ➔ RIDER_ASSIGNED ➔ OUT_FOR_DELIVERY ➔ DELIVERED
🍳
2. Kitchen Engine, Dynamic ETA & Physical Machine QC
Continuous ETA matching, structured delay reasons & barcode/QR package validation
  • Continuous ETA Recalculation: Matches predicted_ready_at against predicted_rider_arrival_at with an eta_confidence_score, continuously recalculating to dispatch riders at the precise moment food is bagged.
  • Structured Kitchen Delay Attribution: Delays require explicit reason codes (INGREDIENT_DELAY, KITCHEN_RUSH, EQUIPMENT_CHECK) rather than arbitrary unmonitored clicks.
  • Quality-Control Transit Threshold: 35-45 min context-aware thermal alerts monitor food temperature and fresh transit without simplistic biological food safety assertions.
  • Machine-Verifiable Handover: Staff and Rider perform a 4-point verification: Package Barcode/QR scan + Order Short Code + 4-Digit Pickup OTP + Item checklist.
⚡ Inactivity Escalation: Orders unattended for >15 minutes trigger an automated audio alarm on the Store Owner dashboard.
🛵
3. Sarathi Fleet Engine & Offline State Partitioning
Atomic first-arrival claiming, rotating tokens & online/offline action separation
  • Atomic Pickup Claiming: First rider at the counter entering the pickup OTP locks rider_id, rider_name, and picked_up_at in an atomic database transaction.
  • Daily Rotating Sarathi Token: 24-hour rotating token (SR-XXXX) for visual verification by kitchen staff and customers.
  • Offline Action Partitioning:
    • Safe to queue locally: ARRIVED_AT_KITCHEN, NAVIGATION_STARTED, CUSTOMER_CONTACT_ATTEMPTED.
    • Requires online server verification: PICKUP_VERIFIED, DELIVERY_OTP_VERIFIED, CASH_SETTLED, ORDER_DELIVERED.
  • Doorstep Photo Privacy: Failed delivery proof photos are captured exclusively via in-app camera into a private secured bucket and auto-purged after 7 days (never stored in rider's personal gallery).
💰
4. Multi-Actor COD Cash Reconciliation Ledger
Granular transaction accounting & dual-confirmation settlement chain
  • True Cash Transaction Breakdown:
    cash_received_from_customer (₹500) - change_returned_to_customer (₹250) = net_collected (₹250).
  • Multi-Actor Settlement Chain:
    • Rider deposits cash (rider_declared_amount, declared_by).
    • Cashier counts cash (cashier_received_amount, received_by).
    • Manager signs off (approved_by).
    • If mismatch occurs: Flagged as DISPUTED with settlement ID, cashier ID, timestamp, and receipt image.
🛡️
5. Cryptographic Hash Chaining & Database Integrity
ON DELETE RESTRICT, tamper-proof audit trigger & zero plaintext OTPs
  • Tamper-Proof Audit Stream (foody_order_events):
    • Foreign key uses ON DELETE RESTRICT. Order cancellation != database deletion; historical audit events can never be cascade-deleted.
    • Enforced by PostgreSQL trigger trg_prevent_audit_tamper blocking all UPDATE and DELETE actions.
  • Cryptographic Hash Chaining: Each event hashes its content and binds to the previous_event_hash, making historical tampering immediately detectable.
Event 1 [ORDER_CREATED] ──(SHA256)──➔ Event 2 [COOKING_STARTED] ──(SHA256)──➔ Event 3 [PICKUP_VERIFIED] ──(SHA256)──➔ Event 4 [DELIVERY_VERIFIED]
  • Hashed OTP Security: OTPs are stored exclusively as salted hashes (pickup_otp_hash, delivery_otp_hash) with attempt counters and short expiration windows.
